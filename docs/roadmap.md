## 2. 병렬 규칙

1. 역할은 6 개다: `design`, `frontend`, `core-backend`, `ingestion-analytics`, `consulting`, `infra`(design 은 사양 7.1). 작업 하나 = 역할 하나.
2. 작업의 `files` 는 docs/ownership.md 에서 그 역할의 행 안에 있다. 의존 관계가 없는 두 작업은 같은 파일을 갖지 않는다(`check_docs.py` 검사). 그래서 동시에 돌아도 서로 덮어쓰지 않는다.
3. 공유 계약(openapi.yaml, schema.sql, domain-model.md, visualization.md, consulting.md, ui-design.md, docs/ui, fixtures/advisor, migrations, pyproject)은 `"kind": "contract"` 작업만 바꾼다. 다른 작업이 계약 변경이 필요하면 멈추고 contract 작업을 제안한다(ga 의 `work` 블록 = Proposal).
4. design 은 시각 언어(토큰 · 신호 대응표 · 움직임 규칙 · golden 장면)를 만들고, frontend 는 그것을 구현한다. frontend 는 색 · 크기 · 시간 · 대응을 새로 만들지 않는다.
5. 작업 간 연결은 **인터페이스**(`app/domains/<d>/api.py` 함수, openapi 경로, design/*.json)로만 한다. 의존 작업이 아직 없으면 인터페이스 서명에 맞춘 가짜(fake)로 시험한다.
6. `done_when` 은 실행 가능한 명령(argv) 하나이고, `runner` 가 그 시험 실행기다(`unittest` · `vitest` · `playwright`).
7. **실행 방식 (baseline 확인 2026-10-05):**
   - ga 0.6 노드 풀은 아직 실제 코드를 만들 수 없다. 노드별 worktree 가 없고, 도구가 꺼져 있고, work item 의 의존 · 파일 소유를 모르고, judge 는 pytest/unittest 만 읽고 pip 배포본이 필요하다.
   - 그래서 MVP 는 먼저 **hub 방식**(지시 하나 = 세션 하나)으로 만든다. 노드 풀은 ga 에 이 기능들이 생긴 뒤에 쓴다.
   - work/1 에 `depends_on` · `files` 키가 없어도 이 표에는 그대로 둔다. `export_work.py` 는 그것을 goal 문장에 접어 넣는다.
   - id 는 `CMD-<LETTERS><number>` 이므로 `ga work add` 를 통과한다.
8. 내보내기: `python3 scripts/export_work.py` → work/1 JSON 줄(한 줄에 하나) → `ga work add -` 또는 hub 지시문.
